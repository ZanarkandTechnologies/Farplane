# Skill System References

These harness references make the local skill system auditable without turning
the registry into a second place to maintain skill truth.

## Surfaces

- `skills/registry.jsonl` is generated by `bin/validators/sync_skill_registry.py` from
  `skills/*/SKILL.md` frontmatter, file paths, direct todo lists, and Markdown
  links.
  Flow or graph views should derive visual prominence from observed skill heat,
  structural todo-chain edges from explicit Todo List skill refs, and stable
  adjacency hints from `common_chains` instead of maintained as a second
  hand-authored registry.
- [`composition.md`](composition.md) is the shared contract for a skill's sole
  output, action ownership, handoffs, and lean domain todos.
- This README is the human selection guide. Use it to understand why neighboring
  skills differ and which one should own a request before opening the generated
  registry or individual `SKILL.md` files.
- [`advisors.md`](advisors.md) is the human-facing Advisor System index. It
  groups every current advisor by operator use case while leaving package
  metadata and `skills/registry.jsonl` as inventory truth.
- [`department-taxonomy.md`](department-taxonomy.md) is the Capability Map
  reference: declared department membership, workflow-root selection, and
  artifact-only map containment.
- `skills/harness/graph/` contains the tracked local visualization
  shell. Its generated skill, document, harness, and lifecycle data lives under
  ignored `.farplane/generated/graphs/`, preventing routine refreshes from
  creating repository diffs. The UI is owned by `harness` maintain mode for now so
  these references stay an index plus registry guide.
- If the graph expands beyond skills into repo-wide Markdown or JSON backlinks,
  keep the generator as a maintenance/reporting utility until a dedicated
  harness map surface has a real consumer. `harness` maintain mode should keep
  owning registry correctness and generated audits, while `harness` place mode
  consumes the broader map for placement decisions instead of owning the
  generator or UI.
- Skill-applicable harness capabilities are authored in
  [`docs/systems/skill-system.md`](../../../../docs/systems/skill-system.md) with
  `category: "skills"` and generated into
  [`docs/features/registry.jsonl`](../../../../docs/features/registry.jsonl). Versioned skill
  templates declare structural feature IDs; individual skills declare only an
  optional skill UI surface. Eval presence is derived from `evals/evals.json`.
  `skills/registry.jsonl` is the generated
  skill inventory, not a second hand-authored skill feature registry.
- `qa_checklist.md` is retired. Normal skill guardrails live in first-load Todo
  List `Rule`/`Assert` blocks; behavior cases, deterministic invariants, and
  material judgment belong to evals, validators, and QA or review respectively.

## Skill UI And Feature Progression

Skill-owned UI is the incubation layer for Farplane UI product surfaces. Use it
when a workflow benefits from a focused viewer, form, graph, dashboard, or URL
binding before the workflow is stable enough to become a first-class product
module.

Progression:

1. Skill has no UI: `SKILL.md`, references, scripts, evals, and proof artifacts
   are enough.
2. Skill gets a small UI binding: a local viewer, embedded panel, debug page, or
   URL helps the operator run or inspect the workflow.
3. Skill UI proves repeated value: the workflow is used often, clarifies
   decisions, or exposes a product pattern.
4. Farplane UI absorbs it: the main product shell owns the route, navigation,
   shared state, and visual system.
5. The skill keeps the binding: the route still points back to the owning skill,
   proof surface, or workflow contract.

Default ownership:

- The skill owns workflow semantics, required data, proof expectations,
  scripts, and any early UI binding metadata.
- Farplane UI owns product navigation, shared components, global project/thread
  context, and polished routes once the surface graduates.
- `harness` maintain mode owns generated skill inventory and registry correctness.
- A future harness map surface may own cross-skill or repo-wide UI discovery
  when skill, docs, JSON, and backlink maps become product features.

Use this rule of thumb:

- unproven workflow -> skill-owned UI
- repeated useful workflow -> Farplane UI route backed by the skill
- core product workflow -> first-class Farplane UI module
- niche or deprecated workflow -> keep as a skill UI or remove it

## Human Selection Guide

For advisor-shaped requests, start with the grouped
[`Advisor System Index`](advisors.md), then use this broader table when the
right owner is not an advisor.

Use this table when two skills look similar. It is intentionally prose-first;
`skills/registry.jsonl` remains the machine-readable inventory.

| Need | Use | Why This One | Do Not Use When |
| --- | --- | --- | --- |
| Choose among real options and name a recommendation, or sequence a roadmap | `advise` | It starts from first principles, frames 3 viable choices, names one recommendation, and states the accepted tradeoff; `mode: roadmap` sequences phases whose first proof is a completed loop. | The user already gave a direct execution request. |
| Make a high-stakes or complex recommendation with independent critique | `advise ensemble=auto|max` | It adds three context-selected or all owner-local independent personas, then synthesizes a recommendation with visible dissent and an explicit next owner. | The decision is simple, reversible, already grounded, or only needs concise advice. |
| Compress an artifact, registry, memory file, or docs tree without losing required value | `doc-advisor` consolidate mode | It inventories units, finds the owning contract, scores value versus duplication and staleness, preserves exact source rows when required, routes knowledge to its retrieval owner, rebuilds minimally, and runs a loss check. | You only need a reader-facing summary; use the native or CLI summarization path. You need domain-specific skill-package edits; route the final patch through `harness` maintain mode. |
| Write or revise durable docs so they are clear, consistent, and human-usable | `doc-advisor` | It owns doc-quality checks: reader contract, term consistency, duplicate definitions, stale sections, examples, links, and agent-facing commentary cleanup. | You only need compact evidence or official-doc lookup; state `Grounding:` inline. |
| Choose an honest metric, provider, guard metric, or no-metric rationale; define `metrics.yaml` objectives and guards | `goal-advisor` metric card (`references/metrics.md`) | It turns objectives, eval results, tickets, Goal loops, and proof evidence into a compact metric card with direction, anti-metrics, measurement method, and route hint, plus explicit `metrics.yaml` objective/guard deltas before execution is selected. | You need to execute the loop; use the owning caller such as `harness`, `harness` optimize mode, `impl-plan`, or `review`. |
| "Research X", "how do others do this", "who are the competitors", "find the paper" | `research` | One branch (market, code, papers, synthesis) qualifies candidates at the source and returns a ranked evidence note. | One claim needs grounding (state `Grounding:` inline), or the target is one person or account (`prospect`). |
| Add independent perspectives to a skill that owns an ensemble | `ensemble=auto|max` on that skill | `auto` selects exactly three relevant diverse personas from the skill's `ensemble.yaml`; `max` runs all of them and preserves dissent in synthesis. | The direct path is enough, or the skill does not declare an ensemble file. |
| Watch an existing PR until review agents and checks pass | `commit` PR watch | It owns explicit heartbeat polling, project-local PR review memory, normalized PR verdicts, fix loops, and terminal notifications while reusing the task's assigned checkout and reviewer-agent review. | You only need one explicit material review (`review`). |
| Choose how to prove a behavior claim; check, scaffold, onboard, and run harness-native evals | `eval` | It picks proof cases (real failures first, small batches, an anti-cheat control) and the proof surface per case, initializes/discovers clean-room eval tasks, judges boolean/tier outcomes, keeps difficult reusable cases as ordinary runnable regressions, and can preserve one isolated CLI run as a scored `behavior_trace` with prompt, events, logs, output, checkpoints, artifacts, schema verdict, and baseline comparison. | You need adversarial tester/evidence-review orchestration or only native-subagent evidence; use `qa` adversarial mode. |
| Test a feature, skill, prompt, or workflow adversarially | `qa` adversarial mode | It designs cases, runs or drafts a tester lane, attacks the tester evidence with an evidence-review lane, reconciles fixes/reruns, and can include Eval `behavior_trace` capture. | You only need one cheap CLI conformance probe and no adversarial proof loop. |
| Apply a normal skill guardrail | The owning Todo List `Rule`/`Assert` | It keeps the instruction beside the workflow node that needs it. | The guard is a repeatable behavior case, deterministic invariant, or material judgment; use eval, a validator, QA, or review. |
| Debug, clean up, review a diff, harden, or audit code | `code-health` | One pass picks one mode (debug, clean, review, harden, audit), applies the lean gate (first sufficient build rung), changes the smallest thing, and returns proof plus residual risk; review mode returns the `patch_correct` JSON used by pre-push reviewers. | The work needs a TAS verdict, completion receipt, or evidence-bundle judgment; use `review`. You only need to locate or explain code; use the `explore` agent. |
| Judge whether a completed plan, implementation, evidence bundle, or reusable fixture is trustworthy | `review` | It applies docs-owned rubric families through a callable TAS wrapper and surfaces blockers before completion claims. | You still need to gather evidence; use QA/test skills first. |
| Prove a user-visible or operated workflow | `qa` (functional, visual, or adversarial mode) | QA owns operated evidence, screenshots, browser/media behavior, case coverage, and proof bundles that review can later judge. | The claim is purely judgment-heavy, deterministic, or behavioral-regression oriented; use `review`, a validator, or `eval`. |
| Decide where a Farplane harness improvement belongs | `harness` place mode | It compares root policy, global templates, skills, subagents, hooks, tickets, validators, registries, and docs before recommending the owning surface. | The user already named the target skill or file and asked for a direct edit. |
| Fix a harness behavior end to end | `harness` | It orchestrates gap diagnosis, placement, eval/proof, optional metric experiment, implementation routing, and review without absorbing the lower-level skill jobs. | You only need a placement recommendation; use `harness` place mode directly. |
| Route extracted durable knowledge | `harness` maintain mode + `doc-advisor` + `manage-wiki` | Send reusable operational procedures to skills, project knowledge and articles to their owning project docs, and sourced entities to canonical Wiki articles. | The input is still raw or unbounded; first bind a source/evidence window and produce explicit deltas. |
| Frame an idea or request and play it back before building | `problem-framing`, `brainstorm`, `recap-idea` (shortcuts) | It splits the requested artifact from the real problem, widens options only when unclear (with `ensemble=auto|max` on request), recommends the smallest boundary from manual service to platform, and plays it back as the view that matches the operator's verification question with one to three correction questions. | You need evidence-backed history from a paused task; read the task's GitHub issue and its latest progress comment. You are choosing among options that are already real; use `advise`. |
| Decide and craft native Goal mode | `goal-advisor` | It compiles listed files, trigger mode, budget, metric, and proof into active Goal, heartbeat, batch, feedback loop (human feedback as the metric via its human-feedback preset), rollout, skill-improvement loop, or direct work, and can emit the final native `/goal` prompt. | The task is tiny and deterministic; work directly without Goal mode. |
| Harden or refine skills, or maintain skill metadata | `harness` maintain mode | It owns `harden_skill` for turning fresh lessons, troubles, ticket progress findings, interval reports, and proof failures into evals, gotchas, blockers, or tickets; `refine_skill` for consolidating older evals/gotchas and shortening skills; plus bulk upkeep, source ownership, and registry regeneration. | The task is broader harness placement; start with `harness` place mode. Use `harness` optimize mode only for measured variant/search loops. |

Agent testing stack:

```text
qa adversarial mode orchestrates serious proof
  -> tester lane gathers evidence
  -> Eval behavior_trace captures CLI child-agent behavior when useful
  -> evidence-review lane attacks proof strength
  -> main agent fixes, reruns, or records a blocker
  -> review/final proof-bundle check judges readiness
```

Use Eval `behavior_trace` alone for cheap CLI skill or prompt conformance probes.
Use `qa` adversarial mode for `$test`, "please test properly", app readiness, or any
claim where the evidence itself needs a skeptical lane.

## Frontmatter Contract

Keep frontmatter small.

Manual fields:

- `description`: required one-sentence functional routing definition, 220
  characters or less. Prefer
  `Use for "<phrase>", "<phrase>": <what it does and returns>` with 2-4
  operator phrases; move long phrase catalogs, examples, model maps, and detailed routing rules into `SKILL.md` or
  references.
- `source`: required, `local` for Farplane-owned skills or `external` for
  upstream-backed skills that should stay syncable with an outside source
- `skill_template_version`: optional structural baseline for skills onboarded
  to a known Farplane skill template version; absence means the skill has not
  been onboarded yet
- `skill_ui`: optional path or route for a skill-owned UI, viewer, dashboard,
  debug page, or UI binding
- `department`: required on a skill that sits on a specialist desk (it must match
  the desk's department); optional on a helper. One canonical operating department from
  [`config/skill-departments.toml`](../../../../config/skill-departments.toml)
- `capability`: optional static projection into the Capability Map and Office:
  `artifact` declares exactly one output family in `produces` and optional
  `consumes`; `integration` declares the artifact families it `consumes` at its
  system boundary; `shortcut` has no additional fields and is not displayed.
  An output-to-input match yields one directed artifact-flow edge. Treat locale,
  campaign, and content variants as invocation data, not new capability IDs.
  Named runtime profiles are separate restriction policies and never belong in
  skill frontmatter. The generated base configuration enables every installed
  skill. Farplane agent metadata must not hide a default skill with
  `allow_implicit_invocation: false`. Named profiles may narrow that set.
  The Capability Map is source-visible, so absence from an active-session list
  under a named profile never means the
  source skill was deleted.
- `methods`: optional child-method contracts. Each declares a parent-qualified
  `id`, `class` (`artifact`, `integration`, or `internal`), and one `output`.
  They are technical Skill Library interfaces, not Capability Map or Office
  nodes.
- `common_chains`: optional one-way adjacency hints, on a skill with a department
- `upstream_url`: optional for `source: external`
- `template_uses.skill-surface-budget`: optional opt-in marker for
  `FEAT-0062` capped skill surfaces; subscribed skills must fit 10 top-level
  todos and 5 eval tasks

Generated fields:

- `path`
- `description`
- `has_checklist`
- `version`
- `skill_template_version`
- `eval`
- `skill_ui`
- `todo_skill_refs`
- `allowed_tools`
- `source`
- `upstream_url`
- `skill_links`

Use `common_chains` only for local forward handoffs:

```yaml
department: operations
common_chains:
  after: ["goal-advisor"]
```

Use capped skill surfaces only after a skill fits the budget:

```yaml
template_uses:
  skill-surface-budget: "0.1.0"
```

If a skill is over budget, run `harness maintain refine_skill` with
`doc_advisor(mode = consolidate, ..., structure = skill)` before enrolling it.

Do not add `before`; reverse lookups should be derived by tooling.

Do not add hand-authored `workflow`, `workflow_steps`, priority, pinning, or
manual importance metadata. Skill graph importance comes from observed skill
heat. If generated todo-chain structure is wrong, rewrite the skill's Todo List
so intended skill calls appear there as explicit refs in the right order.

## Commands

```bash
python3 bin/farplane.py lint skills      # read-only skill/package contracts
python3 bin/farplane.py skills sync       # refresh registry and graph projections, then lint
python3 skills/harness/scripts/check_skills.py --write
python3 bin/validators/sync_skill_registry.py --write
python3 bin/validators/sync_skill_registry.py --check
python3 bin/validators/check_skill_capabilities.py validate
python3 skills/harness/scripts/generate_skill_graph.py
python3 skills/harness/scripts/check_skills.py --template-version 0.2.0
```

Run `python3 skills/harness/scripts/check_skills.py --write` after
editing skill frontmatter, `SKILL.md` Markdown links, or first-load todo lists.
Use the lower-level commands when debugging one specific failure.
Use `--template-version <version>` as a non-failing rollout report for skill
template onboarding. Versioned skills are structurally checked even in report
mode: the current template rejects generic `## Job` sections, requires the
template spine, and requires numbered top-level todo items. Add
`--require-template-version` only when a migration is intentionally ready to
fail missing or non-current skills.

## First-Load Todo Link Contract

Which skills are entrypoints comes from the Capability Map's specialist desks (see [`system.md`](system.md)). First-load todo links are
authoring guidance, not a lint rule. Phase-protocol steps are not skill links;
they are inherited from `runtimes/AGENTS.md`.

When ranking which skill to improve next, use
[`docs/features/FEAT-0064-skill-signals.md`](../../../../docs/features/FEAT-0064-skill-signals.md).
It exposes direct heat, composition heat, maintenance burden, uniqueness, and a
maintenance recommendation. Do not confuse those signals with skill-local eval
scores.

- Domain todos link `research` with its branch, plus peer domain
  skills when a handoff needs one.
- Domain todos do not link core primitives such as `advise` or
  `doc-advisor` consolidate mode directly unless the skill owns that
  primitive step as part of its first-load contract.
- Native Codex phases own generic planning and execution. Artifact-producing
  domain skills such as `impl-plan` and `goal-advisor` own
  their specialized plans, tickets, and work programs.
- `review` is a callable TAS wrapper over docs-owned rubrics in
  `skills/review/references/rubrics/*`.

## Domain Pipeline Shape

For the system-wide function model, use
[`docs/fundamentals/harness-algebra.md`](../../../../docs/fundamentals/harness-algebra.md). This section is
only the skill-specific shorthand for complex domain pipelines.

Complex domain skills may use a compact algebraic model when they decompose
work into components and choose methods per component:

```text
DomainPipeline := Model + MethodRegistry + TodoRecipe + Templates + Proof
```

Keep the first-load workflow in `SKILL.md`. Put longer domain notation in
targeted references such as `references/model.md`, method records in JSON or
Markdown references, and output shapes in `templates/`. Do not add skill-local
`README.md` files just to restate the model.

## Installed Skill Rendering

Repo source packages keep first-load todo truth in `SKILL.md`:

- `SKILL.md` owns the workflow contract, trigger conditions, and references.
- `SKILL.md` must include a direct marker-delimited `## Todo List` section when
  a skill has required every-invocation todo items. This section is the
  first-load todo list, not a final review list. Use numbered markdown todos
  for sequential work and branch choices; use plain `- [ ]` todos only as
  embedded verification/detail checks under a numbered todo.
- Skill-local `todos.md` sidecars are unsupported. Move any useful checklist
  content into the marker-delimited `## Todo List` in `SKILL.md`, then delete
  the sidecar.

`install.sh` and `skills/harness/scripts/install_selected_skills.py` render installed skill
packages instead of symlinking skill directories directly. Installed packages
copy the source `SKILL.md` first-load contract as-is and do not embed or copy
skill-local `todos.md` sidecars.

This makes the first-load todo list visible on first skill load without a second
todo file. Installed skills are directory symlinks into `skills/`, so source
edits are live in `~/.codex/skills` and `~/.claude/skills` without reinstalling;
rerun install only after adding or removing a skill.

When a useful skill is created first in a live runtime home, move the real
folder into `skills/<name>/`, rerun install to replace it with a link, review
the `description`, `source` and (for a desk skill) `department` frontmatter, then run
`python3 skills/harness/scripts/check_skills.py --write`.

## Skill Self-Healing

Skill repair starts from a grounded failure packet and then uses existing
surfaces instead of creating hidden repair work. The canonical contract lives in
[`docs/features/FEAT-0039-behavior-correction-hardcase-metadata-and-narrow-eval-capture.md`](../../../../docs/features/FEAT-0039-behavior-correction-hardcase-metadata-and-narrow-eval-capture.md).

- repo-owned skill capability fixtures live under `skills/<skill>/tests/`
- installed or external skill mirrors live under `tests/<skill>/`
- deterministic fixture validation lives in `bin/validators/check_skill_capabilities.py`
- local repairs should target repo-owned wrappers, fixtures, registry rows,
  docs, or visible repair tickets
- installed or external skill bodies are not edited unless the operator
  explicitly requests that exact external edit

Project-type exploration belongs upstream of domain execution skills. Use
`skills/setup-advisor/references/project-profiles.md` to seed
`docs/bootstrap-brief.md`, direct clarification, `prd`, and `impl-plan` with
component sets, advice axes, prototype gates, and pipeline handoffs. Domain
skills should consume selected directions and execution packets instead
of rediscovering the whole project profile during implementation.

Project lifecycle is currently a `setup-advisor` reference, not a public
top-level skill. Use
`skills/setup-advisor/references/project-lifecycle.md` for the shared
`bootstrap -> interview -> PRD -> tickets -> native planning phase -> implement -> proof/review -> close`
shape. Generated project `AGENTS.md` carries the compact lifecycle rule plus
technical standards, commands, runtime, and QA paths; there is no second root
rules file. Treat planning and execution as native phases; domain skills own real
artifacts and algorithms rather than inheriting generic skill wrappers.

## Source Ownership

Use `source` to decide where wrapper logic belongs:

- `source: local` means Farplane owns the skill package and may edit its body,
  references, and direct todo list directly.
- `source: external` means the skill package itself is upstream-owned and should
  be refreshable from that source. Keep local Farplane policy in the calling
  skill or another local wrapper, so the external skill can be refreshed with
  minimal merge friction.
- Agents must not directly edit external or installed skill bodies such as
  `~/.codex/skills/*` during self-healing or maintenance unless the operator
  explicitly requests that specific external-skill edit. Use local wrappers,
  mirrored fixtures, registry metadata, or visible repair tickets instead.
- External skills may intentionally omit local todo lists when their operational
  wrapper belongs in a local caller skill. Track the upstream file with
  `upstream_url` when one URL is enough.

## Maintenance Skill

Use `skills/harness/` for bulk source, todo, registry, and
consolidation work. Keep this module's docs as the registry contract; keep the
step-by-step maintenance workflow in that skill.

When skill standards or optional skill capabilities change, update
[`docs/systems/skill-system.md`](../../../../docs/systems/skill-system.md) and regenerate
[`docs/features/registry.jsonl`](../../../../docs/features/registry.jsonl) as the supported
feature catalog. Skill template versions carry structural `FEAT-####` handles;
skill packages carry only the optional skill UI field while eval presence is
derived from the canonical path. `harness` maintain mode should report stale or missing adoption from template
version rollout, generated skill inventory, local surface fields, and feature
rows rather than requiring long per-skill migration histories.

Use `harness` place mode before maintain mode when the question is
broader than skills: it compares root policy, global templates, feature docs,
skills, subagents, hooks/scripts, ticket contracts, validators, and registry
metadata before recommending the owning surface.

## Skill Capability Tests

High-value skills may publish small JSON sanity fixtures for operations that
must keep working. Use these for external API, MCP, generated-registry, file
contract, or local script behavior that callers rely on.

Fixture locations:

- repo-owned skills: `skills/<skill>/tests/*.json`
- installed or external skills mirrored by this repo: `tests/<skill>/*.json`

Fixtures for installed or external skills are mirrors and diagnostics, not
authorization to patch the upstream or installed skill body. A failing fixture
should create or update a visible repair ticket that targets a local wrapper,
registry/test metadata, or an explicitly approved external-skill edit.

Keep fixtures small. They should name the operation, the expected behavior, any
sanitized observed failure, the expected recovery decision, forbidden actions,
fallback methods when a connector has multiple tool surfaces, and evidence
refs. Do not store bulky API payloads, secrets, raw transcripts, or full
expected result objects.

Run:

```bash
python3 bin/validators/check_skill_capabilities.py validate
python3 bin/validators/check_skill_capabilities.py list
python3 bin/validators/check_skill_capabilities.py score --skill pm --operation compact_task_context
```

Capability fixtures are discovery and repair inputs. The generated skill
registry may expose compact handles later, but it should not embed bulky
expected results.
