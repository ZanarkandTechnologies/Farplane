# Farplane Framework V1

Farplane Framework V1 is the canonical project operating model. It uses one
Work Pulse, tickets as durable state, bounded scheduled ticket sources, and a
separate self-improvement supply lane. This document preserves the derivation
and rejected alternatives while the linked owner docs define operational
mechanics.

Use the owner docs for operational detail:

- [Lifecycle](lifecycle.md) — end-to-end framework overview.
- [Project Files](project-files.md) — tracked and generated state ownership.
- [Work Pulse And Scheduled Ticket Sources](pulse-and-interval-loop.md) —
  dispatch, planning, reports, Feed Scout, and Dogfood coordination.
- [Ticket Execution Loop](ticket-execution-loop.md) and
  [tickets/README.md](../../tickets/README.md) — Goal Packets, execution,
  evidence, review, and closeout.

## 1. Kernel

The smallest useful model is:

```text
Farplane = program + progress
```

```text
program  = durable instructions for choosing and performing work
progress = observations and state needed to resume without hidden chat memory
```

One step is:

```text
step(program, progress, context?) -> action + progress_delta + next_wake?
```

The minimal project program is:

```text
if an executable ticket exists:
  do the ticket
else:
  plan a bounded next wave
```

Tickets are the practical state primitive. Kanban, reports, metric snapshots,
and registries are projections or context; they are not a second ontology.

## 2. Work Pulse

```text
work_pulse(program, goals, metrics, tickets, context?, policy)
  -> reconciliation
   + worker_handoffs
   + review_reminder?
   + ticket_deltas
   + planned_wave?
```

Work Pulse is the only project heartbeat. It:

1. reconciles ticket and worker state;
2. derives executable ordinary tickets and matured check-ins;
3. dispatches work up to available worker capacity;
4. releases workers when tickets wait for humans or external signals;
5. asks the BAU planner for a bounded wave only when the executable board is
   empty; and
6. may send at most one ticket-owned review reminder whose due time has
   matured.

Planning and dispatch use different limits:

```text
plan_next_wave(..., wave_size = m) -> 0..m ticket_specs
dispatch(executable_tickets, idle_workers = n) -> 0..n handoffs
```

`review_wip` is backpressure, not worker occupancy and not an automatic chase
trigger. Queue size may stop additional review-producing work; reminder due
state comes from the ticket's `progress.md` Review block.

## 3. Minimal Ticket State

Ticket frontmatter carries identity, lifecycle, and sparse routing only:

```text
ticket(ticket_id, title, status, created_at, updated_at;
       priority?, claimed_by?, depends_on?, human_gate?, compute_target?)
```

`status` is the lifecycle truth:

```text
todo | active | awaiting_review | waiting_signal |
blocked | done | failed | rejected
```

- `todo` is ordinary executable work when dependencies are satisfied.
- `active` plus `claimed_by` consumes a worker.
- `awaiting_review` and `waiting_signal` consume no worker.
- a matured Reward row temporarily makes the original `waiting_signal` ticket
  executable for its Check-In Program.
- only `done` satisfies a dependency.

QA strategy, rewards, evidence, review state, blocker detail, verification,
and next actions belong in `ticket.md`, `program.md`, `progress.md`, or
ticket-scoped artifacts—not parallel metadata flags.

## 4. Planning And Context

The BAU planner has one job:

```text
plan_next_wave(harness, goals, metrics, ticket_history, reports?, wave_size)
  -> ranked BAU ticket specs
```

It lists useful levers, proposes bounded ideas, scores compounding value and
urgency, removes duplicates, and ranks executable tickets. It does not invent
harness self-improvement; that is a separate supply lane.

Dated reports and provider observations are optional current context. A new
observation justifies replanning only when it changes a ranked action, clears
a blocker, crosses a threshold, matures a check-in, invalidates an assumption,
or changes an authority or safety condition.

Feed Scout and other providers own collection. Stable capability skills remain
workflow-pure and receive fresh evidence as inputs.

## 5. Scheduled Ticket Sources

Recurring jobs are bounded sources, not additional heartbeats:

| Source | Primary output | Ticket authority |
| --- | --- | --- |
| Feed Scout | dated external-evidence report | bounded source-backed opportunities |
| Daily Interval | BAU problem report | deduped, already-evidenced maintenance |
| Weekly Interval | longer-window BAU problem report | deduped, already-evidenced maintenance |
| Dogfood Review | experiment portfolio report | bounded self-improvement Goal Packets |
| Operator | explicit direction or correction | explicitly requested tickets |

All sources feed the same ticket board. Only Work Pulse executes tickets and
performs matured check-ins.

Interval reports preserve a small Problems ledger. They may carry unresolved
problems forward and resurface known maintenance, but they do not own new BAU
direction, Feed Scout collection, reward execution, or broad
self-improvement planning.

## 6. Self-Improvement

Skills, workflows, planners, automations, policies, hooks, validators, and
feature bundles may be improved as bounded surfaces:

```text
improve(surface, objective, feedback_class, proof_policy)
  -> experiment_ticket + evidence + promotion_decision?
```

Two operators describe most improvements:

```text
harden(surface, metric, cost_ceiling)
  -> increase robustness or quality within the cost ceiling

refine(surface, quality_floor)
  -> reduce complexity, context, latency, or operations above the quality floor
```

The weekly Dogfood lane reviews active and recent experiment tickets, prior
outcomes, metrics, dogfood findings, and transfer candidates. It writes a
portfolio report and may create a capacity-limited, non-interfering next wave.
It does not execute the experiments it proposes.

### Proof Routing

Choose the cheapest honest feedback path:

| Situation | Default route |
| --- | --- |
| Named invariant or required capability is clearly missing | adopt, verify, monitor, and retain rollback |
| Adjacent behavior could regress | deterministic replay or bounded local proof |
| Slow real outcome has a representative proxy | toy project or simulation, then bounded pilot |
| Agent, prompt, skill, or workflow behavior is uncertain | eval, behavior test, or ablation |
| Human judgment is the honest metric | `optimize-with-human` with recorded feedback |
| No faithful fast signal exists | delayed pilot with maturity, budget, guard, and rollback |
| No credible feedback provider exists | reject or defer |

“Logically better” does not waive proof. Direct adoption is reserved for a
named gap with bounded blast radius, direct verification, monitoring, and a
clear rollback.

### Immediate And Delayed Reward

Immediate feedback stays inside one Goal-backed execution:

```text
baseline -> candidate -> compare -> keep / revise / reject
```

Delayed feedback stays on the original ticket:

```text
intervention
-> record baseline, exposure, Reward, and Check-In Program
-> status: waiting_signal
-> Pulse derives maturity
-> worker runs program.md
-> accept / kill / monitor with next check-in
```

There is no separate check-in ticket, daily check-in controller, or Taste Loop
heartbeat. Human-feedback optimization is an ordinary self-improvement ticket.

### Doctrine Promotion

One successful experiment changes its bounded surface; it does not
automatically become general policy. Reuse requires a transfer test:

```text
accepted experiment
-> pattern candidate
-> transfer test on a similar problem
-> scoped doctrine
-> bounded rollout tickets
```

The promotion record preserves the pattern's scope, preconditions, evidence,
known counterexamples, transfer tests, rollback, and next review time. Failed
transfer remains useful counterevidence and narrows the doctrine instead of
being hidden. Dogfood may propose promotion or rollout work, while the owning
ticket and reviewer evidence justify the decision.

## 7. Capability And CRM Boundaries

Recurring artifact factories are capability skills called by Work Pulse. They
do not need product-local controllers merely because they produce different
artifacts.

A capability deserves independent state only when it has a genuinely distinct
event stream, authority boundary, budget, or prioritization policy that cannot
be represented by the shared board and skill contract.

Long-lived prospects and customer relationships are CRM records, not BAU
tickets:

```text
crm_record -> bounded_action_ticket -> outcome_writeback -> crm_record
```

The ticket owns one action or experiment. The CRM owns relationship state,
funnel position, and waiting time. A waiting prospect therefore consumes
neither a worker nor review WIP.

Content-market optimization is also outside the kernel. Tasty Packs may supply
ideas and market priors; high-volume variant launching requires its own budget,
interference, and platform-policy contract before becoming a framework
feature.

## 8. Project File Ownership

| Surface | Owns |
| --- | --- |
| `farplane/harness.md` | stable project charter, authority, guardrails, capability refs |
| `farplane/goals.yaml` | current value direction, KPI selection, bets, holds |
| `farplane/metrics.yaml` | provider-independent metric meaning |
| `farplane/bindings.yaml` | safe provider coordinates and refresh recipes |
| `farplane/automations.toml` | explicit recurring and event-triggered invocations |
| `farplane/hooks.json` | optional deterministic hook configuration |
| `tickets/TASK-*/` | work, program, progress, evidence, QA, review, check-ins |
| `.farplane/reports/` | derived cross-ticket and scheduled reports |
| `.farplane/metrics/` | generated metric observations |
| `.farplane/registries/` | optional generated projections with a proven consumer |

There is no generic evidence or review bucket: proof stays with the ticket that
makes the claim. There is no mandatory registry directory or hand-maintained
ticket index. Runtime state must use an owner-named path rather than becoming a
second source of truth.

## 9. Migration Decisions

The implementation landed in bounded workstreams:

| Workstream | Tickets | Result |
| --- | --- | --- |
| Work Pulse | `TASK-0318` | retired product-scoped Pulse and introduced one project dispatcher/planner boundary |
| Scheduled sources | `TASK-0319`, `TASK-0320` | narrowed Interval, separated Feed Scout and Dogfood, moved check-ins to Pulse |
| Project files | `TASK-0321`, `TASK-0322` | retired product files, introduced `metrics.yaml`, narrowed bindings and manifest |
| Minimal state | `TASK-0326` | minimized ticket metadata, retired Taste Loop, made review waits worker-free |

The migration corrected these causal failures:

| Problem | Consequence | Replacement |
| --- | --- | --- |
| Artifact categories became product-local controllers | broad project judgment fragmented into duplicated strategy, state, budgets, and Pulse loops | capability skills plus one shared project Work Pulse |
| Interval and product planners both chose direction | overlapping ticket supply, unclear authority, and duplicate work | BAU planner owns new direction; Interval only reports and resurfaces evidenced maintenance |
| Check-ins were coupled to report cadence | matured experiments could wait for an unrelated Daily or Weekly workflow | Pulse derives maturity from the original ticket Reward and runs its program |
| Findings accumulated schema instead of decisions | metadata and registries grew while evidence ownership became less clear | compact report Problems ledgers and ticket-scoped evidence |
| Advanced learning machinery preceded the minimal board proof | attribution, variants, and controller design obscured whether one worker could empty one board | prove execute-or-plan first; add capacity and experiment methods only from observed need |
| Human or external waits occupied execution concepts | workers and BAU capacity appeared blocked by dormant state | `awaiting_review` and `waiting_signal` release workers and use explicit wake conditions |

Rejected alternatives:

- product categories as independent runtime controllers;
- Interval as a second general planner;
- a separate executor for improvement tickets;
- daily or weekly check-in controllers;
- parent/child tickets solely to represent experiment rounds;
- concatenating every harness surface into one self-editing prompt;
- generic `.farplane/runtime`, evidence, review, or mandatory registry buckets;
- treating every prospect or long-lived relationship as a BAU ticket.

## 10. Proof And Falsification

The structural migration is implemented. Representative operation should keep
testing these claims:

| Claim | Required representative proof | Falsifier |
| --- | --- | --- |
| One Pulse can empty the board | existing ticket dispatch plus empty-board bounded refill | planner runs despite executable work, or no bounded refill occurs |
| Limits remain distinct | wave, worker, review, and experiment capacity receipts | any configured cap is exceeded |
| Scheduled sources stay bounded | independent Feed Scout, Interval, and Dogfood reports | a source executes tickets or invents work outside its authority |
| Check-ins need no controller | matured and future Reward rows on one ticket | matured row is missed or future row executes early |
| Shared execution is sufficient | ordinary and improvement tickets use the same worker path | improvement requires a separate executor |
| Proof routing is honest | direct, toy/eval, human, or delayed evidence matches the claim | change is promoted without a credible feedback path |
| Capability boundary is sufficient | capability work runs from skill plus ticket context | recurring work requires irreducible separate authority or state |

Remaining questions should be answered from run evidence:

1. Does improvement work need any explicit classification beyond its Reward and
   proof program?
2. What observed thresholds should distinguish adopt-and-monitor from a toy,
   human-feedback, or delayed proof?
3. What is the minimum useful materiality and deduplication rule for external
   context events?
4. How many successful transfer tests and what counterevidence threshold should
   be required for each doctrine scope?
5. Is a persisted due-check projection ever needed, or is derivation at Pulse
   time sufficient?

## 11. Before, After, Example

> **Before:** Product-scoped Pulse controllers and a broad Interval workflow
> split planning, execution, reporting, check-ins, maintenance, and
> self-improvement across overlapping loops.
>
> **After:** One Work Pulse executes a shared board; BAU planning, Feed Scout,
> Interval reporting, and Dogfood improvement are bounded ticket sources;
> delayed feedback resumes the original ticket's program.
>
> **Example:** Daily Interval carries forward a repeated stale-link problem and
> creates one deduped maintenance ticket. Dogfood separately proposes an
> immediate toy/eval improvement while a delayed pilot remains dormant. Pulse
> executes both ordinary and improvement work, releases workers on review or
> signal waits, and later resumes only the matured Reward row.
